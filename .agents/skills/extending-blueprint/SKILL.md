# Extending Blueprint

## Overview

Changes in this repo are not just local code edits. Blueprint's generators, runtime, sample consumers, docs, migration plan, and repo-local skills form one contract. A safe change preserves compile-time behavior, deterministic harnesses, and the preferred consumer story together.

## When to Use

- Modifying generator discovery, descriptors, app registration, pipelines, or runtime execution
- Adding module seams, diagnostics, manifests, or inspection surfaces
- Changing the sample consumer story, migration workflow, or Blueprint-specific agent guidance
- Reviewing whether a Blueprint change also requires docs, sample, or skill updates

Do not use this skill for ordinary downstream app usage; use `using-blueprint`.

**REQUIRED BACKGROUND:** Use `using-dotnet`, `dotnet-advisor`, `test-driven-development`, and `verification-before-completion` for this work. Use `systematic-debugging` when tools behave unexpectedly.

## Quick map

| Change area | Start here | Also verify |
| --- | --- | --- |
| Operation contract and descriptors | `docs\architecture.md`, `OperationDescriptorSourceGenerator` | app registration, diagnostics, sample usage |
| App registration | `AppDataModelSourceGenerator` | generated `this.Register(Operation.Configure())`, runtime registry |
| Pipelines and executors | `OperationExecutorPipelineSourceGenerator` | handler discovery, full pipeline snapshots, compile-time source checks, runtime integration harness, concurrent/startup stress harnesses, benchmark harness (`src\Blueprint.SourceGenerator.Benchmarks`) |
| Diagnostics and validation | `docs\compile-time-validation.md` | precise source locations, stable IDs, tests |
| Manifest and inspection contracts | `migration\generated-manifests-and-inspection-surfaces\plan.md`, `GeneratedManifestEnvelope`, `BuildDebugManifest(...)` | `docs\observability-and-dev-experience.md`, snapshot proof, contributor ownership collisions |
| Consumer story | sample projects + `docs\refactoring-workflow.md` | `using-blueprint`, migration prompt, docs |

## Working rules

1. Start in `/docs`, then find the deterministic harness before touching production code.
2. Preserve incremental cacheability and review the generated diff, not just handwritten files.
3. Follow through across generator, runtime, sample, docs, and skills when the contract changes.
4. Treat the sample consumer as part of verification, not polish. If a change affects consumer-visible contracts, generated registration/output, or sample-visible workflow, verify `src\Blueprint.SourceGenerator.Sample` still demonstrates the current contract and update it in the same change when it drifts.
5. If Blueprint becomes easier or harder to consume, update `using-blueprint` in the same change.
6. If the repo-internal extension workflow changes, update this skill in the same change.
7. For migration orchestrator work, keep `migration\progress.json`, `migration\plan.md`, and the relevant workstream plan aligned. Treat the JSON file as the machine-readable resume index, not as a replacement for the plan narrative.
8. For migration orchestrator work, finding the next ready slice is not enough. The same session must continue into failing proof and the first implementation step unless an explicit blocker or review gate stops the change.
9. Concrete module implementations must end with `Module`, live in dedicated subfolders under `src\Blueprint.SourceGenerator\Modules`, and keep module-specific helper files beside the owning module in that folder.
10. Contributor seam methods should use explicit `ContributeTo<Thing>` names, and planning context classes should prefer helper methods with only a small read-only metadata surface rather than record-style public inner state or mutable plan/execution access.
11. For pipeline planning, prefer helper APIs that imply stage participation when contributors register render steps or variables; do not reintroduce manual `AddContribution(...)` bookkeeping.
12. For exception-translation extension work, contribute translators through `IExceptionTranslationContributor` (the built-in translator set now comes from `DefaultExceptionTranslationModule`) and resolve `PipelineExceptionTranslatorPolicy` from the ordered execution-plan contributors. Do not recreate default translators independently inside descriptor or pipeline generators, or descriptor failure metadata, `BP113` overlap detection, and host failure translation will drift.
13. For pipeline contributor feature work, require the full proof matrix: a full pipeline snapshot, compile-time invalid-configuration or source-check tests when the generator can validate the contract, and runtime integration tests that execute the generated pipeline for valid and invalid paths. A substring assertion alone is not enough.
    - For handler-return work specifically, keep normalization static in generated code rather than adding runtime type switching, and prove the nullable plain-value, unsupported-union-member, and declared-contract mismatch paths through the `BP105`-`BP107` diagnostic seam.
    - For descriptor result-contract work, project new metadata through additive `ApiOperationDescriptor.SetFeatureData(...)` surfaces such as `OperationResultOutcomesFeatureData`, keep contract-only compilations able to skip runtime-only result metadata gracefully, and prove both generated descriptor text and runtime `Configure().GetFeatureData<...>()` behavior.
    - For OpenAPI/HTTP response-metadata slices, build on `HttpResponseMetadataModule` so HTTP-exposed descriptors merge flattened semantic success outcomes with `FailureOutcomesModule` metadata into `OperationHttpResponseMetadataFeatureData`; keep status code, response-body presence, semantic result names, and compile-time-known body type names flowing through that seam instead of rediscovering exception policy, payload typing, or executor response mapping inside later OpenAPI document builders. Serializer-context follow-ons should derive parallel coverage metadata from `BodyTypeNames` (for example `OperationSerializerContextCoverageFeatureData`) and now flow that contract through the app-owned declaration seam: `[BlueprintAppSerializerContext(JsonSerializerContextType = typeof(...))]` on the app root plus the generated `BlueprintApp.AppOwnedSerializerContext`, `AppOwnedSerializerContextType`, `AppOwnedSerializerContextBodyTypes`, and `AppOwnedSerializerContextBodyTypeNames` assignments. That coverage metadata currently comes from `SerializerContextCoverageModule` as an `IDescriptorContributor` via `ContributeToDescriptor(...)` after `HttpResponseMetadataModule`, while the app-owned declared inventory is parsed once by `AppDataModelSourceGenerator` and persisted on `BlueprintApp` for later schema/document slices. The first runtime OpenAPI follow-on now lives in `Blueprint.Runtime.Http.OpenApiDocumentBuilderContext.Create(app)`, which snapshots app-owned serializer declaration facts plus per-operation `OperationHttpResponseMetadataFeatureData` and `OperationSerializerContextCoverageFeatureData` for HTTP-exposed operations only, including the currently missing declared body payload types per operation. The next runtime follow-on now lives in `Blueprint.Runtime.Http.OpenApiSchemaProjectionContext.Create(document)`, which projects only the covered serializer-backed body types into ordered `OpenApiSchemaModel` entries with broad `OpenApiSchemaKind` values, ordered property-name inventories, and additive `OpenApiSchemaPropertyModel` facts (`Kind`, `IsRequired`, `IsExtensionData`) from serializer metadata. The current response-projection follow-on now lives in `Blueprint.Runtime.Http.OpenApiResponseSchemaReferenceProjectionContext.Create(schemaProjection)`, which preserves each `OperationHttpResponseMetadata` entry while resolving its covered `BodyTypeNames` onto stable per-response `OpenApiResponseSchemaReference` values. The current schema-rendering follow-on now lives in `Blueprint.Runtime.Http.OpenApiSchemaComponentRenderingContext.Create(schemaProjection)`, which renders those projected schemas into reusable `OpenApiSchemaComponentModel` entries with OpenAPI-style type names, ordered required-property names, and ordered property contracts while keeping response, operation, and document assembly deferred. The current response-object follow-on now lives in `Blueprint.Runtime.Http.OpenApiResponseObjectRenderingContext.Create(responseSchemaProjection)`, which binds response status/body/result metadata onto deterministic JSON response-content entries that reference the reusable rendered schema components while still leaving operation assembly deferred. The current operation-rendering follow-on now lives in `Blueprint.Runtime.Http.OpenApiOperationRenderingContext.Create(responseObjects)`, which binds descriptor-published operation identity, ordered HTTP methods, and ordinal-stable URL formats onto those response objects while still leaving path grouping and full document assembly deferred. `OperationHttpMethodMetadataModule` is now the approved compile-time seam for that inventory: it projects explicit `[HttpMethod(...)]` and shorthand HTTP method attributes, falls back to Blueprint's conventional `POST`/`GET` split for HTTP-exposed commands vs. non-commands, and fails blank explicit method declarations at compile time with `BPOA001` instead of letting later OpenAPI work normalize bad metadata silently. The current path-grouping follow-on now lives in `Blueprint.Runtime.Http.OpenApiPathItemRenderingContext.Create(operationRendering)`, which groups operation models into deterministic `OpenApiPathItemModel` / `OpenApiPathItemMethodModel` contracts keyed by route template and HTTP method while deliberately retaining same-path/same-method operation lists for later conflict handling instead of collapsing them early. Because `BlueprintApp.Register(...)` still rejects duplicate URL formats across descriptors, cross-descriptor same-path grouping is currently a synthetic operation-model proof rather than a generated-app registration scenario; preserve that boundary until a later plan explicitly widens runtime URL registration semantics. The next narrow follow-on should therefore render the final OpenAPI document model from those path items rather than widening registration behavior in this slice. Reuse `DescriptorPlanBuilder` so app-level coverage validation and descriptor generation consume the same contributor composition and exception-translation policy, and keep later OpenAPI document/schema work extending those app/runtime seams rather than routing through `BlueprintHttpOptions`, executor inspection, or ad-hoc type-name lookups.
    - For flattened outcome alignment checks, use `BP111` to fail descriptor generation before `OperationResultOutcomesFeatureData` can drift away from the declared `Results<T1, T2>` semantic member set; nested unions and plain CLR payload members should not be projected as descriptor outcomes.
    - For host-result availability checks, reuse flattened semantic-result analysis plus `HostExposureRegistration` metadata so host-exposed operations fail at compile time with `BP108` when declared result contracts outrun the current enabled executor/adapter surface.
    - For host-translation ambiguity checks, keep the rule distinct from missing-executor validation: only report `BP109` when supported semantic union members still collapse to the same current host response shape, and keep unsupported members owned by the earlier `BP108` seam.
    - For no-result-shape separation checks, use `BP112` to keep host-neutral `NoResultOperationResult` distinct from host-owned no-content/status-only result families such as `Blueprint.Runtime.Http.HttpNoContentResult`; unsupported members still belong to `BP108`, and same-status body/no-body unions still belong to `BP110`.
    - For HTTP union discrimination checks, reserve `BP110` for supported same-status unions that still lack an explicit host/client discrimination strategy even when the current host response shapes differ (for example body-bearing `200` plus empty-body `200`), leaving same-shape collisions with `BP109`.
    - For runtime-result migration slices, keep host-owned translation explicit (for example `HttpOperationResultExecutor`) and preserve a deliberate fallback boundary when only part of the legacy self-executing path is being retired. Lock host-neutral `NoResultOperationResult` to the default empty HTTP `200 OK` path, keep host-neutral `CreatedResult<T>` on the body-bearing HTTP `201 Created` path, keep host-neutral `AcceptedResult<T>` on the body-bearing HTTP `202 Accepted` path, keep host-neutral `NotFoundResult<T>` on the body-bearing HTTP `404 Not Found` path, keep host-neutral `ConflictResult<T>` on the body-bearing HTTP `409 Conflict` path, keep host-neutral `KeyOnlyResourceEventResult` on the empty HTTP `201 Created` convention path, keep explicit HTTP `204`/status-only/plain-text conveniences in host-owned result families such as `Blueprint.Runtime.Http.HttpNoContentResult`, and in the trimmable runtime project prefer serialization paths that do not introduce new trim warnings-as-errors.
    - For validation-failure canonicalization slices, move generator-owned validation paths to the canonical `Blueprint.Runtime.Exec.ValidationFailedResult` name, keep `Blueprint.Middleware.ValidationFailedOperationResult` available only as a compatibility alias or shim, and preserve the current `BP108`/unsupported-host boundary until the broader error-model work deliberately widens host translation for semantic failure results.
    - For unhandled-exception canonicalization slices, generate the outer catch shell to construct `Blueprint.Runtime.Exec.UnhandledExceptionResult`, keep `Blueprint.UnhandledExceptionOperationResult` available only as a compatibility alias, and keep both names internal-only so declared contracts still fail through `BP111` instead of leaking fallback exception shells into public descriptor outcomes.
14. For validation or executor hot-path work, run `src\Blueprint.SourceGenerator.Benchmarks` and review the BenchmarkDotNet artifact before handoff or commit. Keep deterministic checks in the `pull-request lane`, and move noisier wall-clock or higher-volume comparisons into a `scheduled/manual` lane instead of treating shared-runner timing as an ordinary PR gate. When the slice is about stability under concurrency or repeated startup/host mapping instead of pure cost, pair that benchmark evidence with a non-microbenchmark runtime stress proof in tests so the generated executor shell or `MapBlueprintApi(...)` host surface is exercised on the same seam under repeated load. For descriptor-level string/template pressure such as link generation, reuse the synthetic scale harness and prove that a single high-volume link edit stays localized to the affected descriptor output instead of broadening across unrelated generators.
15. For validation fast-path work, keep rule detection and code emission in dedicated strategy helpers beside `ValidationModule`; use `ValidationRuntime` for unsupported per-property fallback and add `BPV` diagnostics when referenced members are provably invalid.
16. For breaking-change or migration-tooling slices, reserve and prove `BPMIG` diagnostics through `src\Blueprint.Migration.Analyzers\MigrationDiagnosticDescriptors.cs`, `src\Blueprint.Migration.Analyzers.Tests`, and `src\Blueprint.Migration.Analyzers.CodeFixes` instead of inventing new analyzer layouts or undocumented ID ranges in ad hoc locations. The live activation cleanup seam now starts with `BPMIG001` for redundant parameterless `BlueprintApiBuilder.AddOpenApi()`, `BPMIG002` for redundant parameterless `AddHateoasLinks()`, and `BPMIG003` for redundant parameterless `AddAuthorisation()`, while the first configuration-required companion rules are `BPMIG100` for configured `AddOpenApi(Action<OpenApiOptions>)` and `BPMIG101` for configured `AddAuthentication(...)`. The first structured report projection for that family now lives in `src\Blueprint.Migration.Analyzers\MigrationReport.cs` and `src\Blueprint.Migration.Analyzers\DiagnosticFinding.cs`, the dry-run collector lives in `src\Blueprint.Codemod\SolutionAnalysisRunner.cs`, the first apply-mode foundation lives in `src\Blueprint.Codemod\ApplyModeOptions.cs` plus `TransformationApplier.cs`, and durable artifact emission now lives in `src\Blueprint.Codemod\CodemodArtifactWriter.cs` plus `CodemodMarkdownSummaryWriter.cs`; extend that shared analyzer/report/codemod seam and its deterministic bucket/documentation-path contract instead of inventing ad hoc migration-report DTOs, separate apply-only plans, output-only shadow models, or one-off collectors when codemod work grows.
17. New manifest producers should extend `Blueprint.SourceGenerator.Artifacts.GeneratedManifestEnvelope` and its default `.blueprint/manifests/<artifact>.manifest.json` layout instead of inventing unrelated top-level JSON contracts or insertion-order-dependent output. Keep the checked-in schema artifact at `src\Blueprint.SourceGenerator\Artifacts\GeneratedManifestEnvelope.schema.json` aligned with that envelope contract, and treat the current operations-discovery payload shape as an approved starting point, not as a forever-frozen contract if later debug-manifest improvements need a better contributor-owned projection. Cross-workstream performance artifacts now follow that same rule too: the Tier 2 synthetic invalidation summary is a `scale-invalidation` envelope with a contributor-owned `synthetic-scale-harness` section, and the first build telemetry contract is a sibling `build-telemetry` envelope with `synthetic-build-harness`; neither should regress into ad-hoc performance-only JSON shapes. The repo-native build telemetry runner is `migration\performance-and-scale\Capture-SyntheticBuildTelemetry.ps1`, and it now emits cold-build, no-op-build, design-time-build, and single-edit-build captures through that same envelope. Any synthetic project it materializes must keep emitted inspection files out of `Compile` (for example with `Compile Remove="artifacts\generated\**\*.cs"`) so repeated no-op or design-time captures do not re-ingest stale generated output.
18. Derived manifest projections such as `GeneratedManifestEnvelope.ToMarkdown()` must read only envelope data, and they should keep nested payload ordering deterministic so future richer manifest content stays reviewable. Hosted markdown fixtures should stay semantically aligned with `GeneratedManifestEnvelope.FromJson(...).ToMarkdown()` rather than drifting from the canonical JSON contract.
19. Runtime inspection slices should load previously built manifest data through stable seams such as `ManifestResourceLoader` plus `GeneratedManifestEnvelope.FromJson(...)`; do not rebuild discovery by calling contributor seams or re-deriving operation metadata in runtime code. If the runtime project itself hosts an inspection surface, prefer serving canonical embedded JSON via an explicit resource-name seam (for example `BlueprintHttpOptions.OperationsManifestResourceName`) instead of adding a `Blueprint.Runtime` reference back to `Blueprint.SourceGenerator`. Richer hosted views such as diagnostics pages should project client-side from that JSON rather than introducing a second runtime-side manifest model, and hosted markdown or schema surfaces should be served as prebuilt embedded bytes (for example via `BlueprintHttpOptions.OperationsManifestMarkdownResourceName` and `BlueprintHttpOptions.OperationsManifestSchemaResourceName`) rather than calling `GeneratedManifestEnvelope.ToMarkdown()` or interpreting schema semantics inside the runtime assembly.
20. Manifest contributor slices should activate the typed `ContributeToManifest(DebugManifestContributorContext)` seam and the public `BlueprintSourceGenerationConfig.BuildDebugManifest(...)` helper instead of bypassing the planning model with ad-hoc envelope writes. Treat per-operation debug-manifest entry keys as contributor-owned: if two contributors need the same concept, redesign the payload or section shape instead of relying on overwrite behavior, because `BuildDebugManifest(...)` should now fail with `BPMOD006` on cross-contributor key collisions.
21. For host-exposure slices, treat the active `IEnabledHostContributor` set as the enabled-host registry: contributors that record `HostExposureRegistration` metadata must have a matching enabled host contributor, unsupported host exposure should fail at compile time with the operation-discovery diagnostic seam, and one operation must not land on more than one enabled host unless a later plan explicitly widens that rule.
22. A generally reusable non-HTTP host may live in the core Blueprint package, but keep its namespaces and public type names obviously host-specific so HTTP and non-HTTP surfaces stay easy to distinguish.
23. When comments are needed, spend them on invariants, fallback boundaries, and trade-offs; never on repeating what the code already says.
24. Prefer `static` lambdas in LINQ or similar delegate-heavy code whenever no local capture is needed.
25. Keep module-specific tests in module-specific files instead of extending shared catch-all test files forever.

## Common mistakes

- Fixing one seam without checking runtime, sample, and docs
- Treating sample-app drift as optional or outside verification
- Adding runtime repair where compile-time validation should exist
- Blindly updating snapshots without reading the generated diff
- Changing consumer-facing behavior without updating `using-blueprint`
- Treating a generated-source line check as the only proof for pipeline behavior
